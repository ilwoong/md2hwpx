# 남은 작업

주석 마커(`<!-- @hwpx ... -->`)를 들인 뒤 이어서 할 일과, 웹 페이지를 고친 뒤 확인할 일. 끝낸 항목은 이 문서에서 지운다.

## 지금 상태 (2026-11-21)

- `feature/deprecate-marker-lines`: 이 프로젝트만의 표기 줄(`[TOC]`·`[새 번호]`·`[감추기]`·`[빈 줄]`·`[여백면]`)에
  폐지 예고 경고(`source.old_markers`), 샘플을 주석 마커로 이전. 샘플 HWPX 는 이전 전후로 같다(필드 id 제외).
- `feature/marker-near-miss` (위 브랜치에서 갈라짐): `@HWPX`·`@hwpx:`·`@hwp`·`@ hwpx`·`@hwpx쪽나눔` 처럼
  마커와 비슷한 주석을 경고 (`parser._LIKE_MARKER_START`, 이유 `'@hwpx 명령' 꼴이 아니어서`).
  띄어 쓴 명령(`쪽 나눔`)에 맞는 이름을 알려 주고 (`모르는 명령이라 (쪽나눔?)`), 스펙에 주석 마커의 한계를 적었다.
  README 에 uv 최소 버전(0.4.27)을 적었다: 그보다 옛 uv 나 `UV_NO_DEV` 에서 `uv run pytest` 가 `Failed to spawn: pytest` 로 실패한다.
- 두 브랜치 모두 main 에 합쳤다 (`feature/marker-near-miss` 의 PR #76 에 둘 다 들어 있다).
- `feature/web-ui-spacing-a11y`: 웹 페이지의 간격·키보드 접근·다크 모드, 선택 옵션 묶음, 고른 파일 목록, 입력 아래의 오류,
  `.env` 의 업로드 크기 제한 (`MD2HWPX_MAX_UPLOAD_MB`), 명령줄 클라이언트(`md2hwpx-remote.py`)와 "스크립트" 탭, 제목 옆의 빌드 날짜.
  main 에 합쳤다. 실제 환경에서 보지 못한 것은 아래 3 에 남겼다.
- `feature/prune-template-styles` (PR #78, main 에 합침): 내장 템플릿의 스타일 정리와 `글머리표` 스타일(아래 4), 그리고
  프로젝트 전체를 리뷰해 고친 것들이다.
  - 폴더 입력은 파일을 하나씩 따로 읽는다 (각주·링크 정의는 파일마다). UTF-8 이 아닌 파일은 오류로 알린다.
    front matter 는 첫 `---` 다음 줄이 `키:` 줄일 때만이다. 줄은 markdown-it 이 세는 대로 센다.
    그림으로 들어가는 이미지만 검사한다.
  - `POST /convert` 는 JSON (`filename`, `warnings`, `hwpx`) 으로 답한다. 세션은 10,000개까지, `/tmp` 는 1GB 까지다.
  - 목록은 그것이 든 항목의 나머지 블록 자리에서 시작한다. 글머리표가 없는 `글머리표` 스타일은 쓰지 않는다.
  - 실제 환경에서 보지 못한 것은 아래 3·4 에, 미룬 것은 5 에 남겼다.

## 할 일

### 1. 없어질 표기 지우기 (폐지 3단계)

- 언제: 쓰는 원고를 변환해도 `없어질 표기입니다` 경고가 하나도 나오지 않을 때. 다른 사용자가 있으면 버전을 올리며 알린다.
- 먼저: 주석 마커가 표기 줄을 거쳐 읽힌다 (`parser._line_command` 가 `"[새 번호{}]"` 를 만들어 `pieces.match_marker` 로 검사).
  마커가 인자를 직접 읽도록 바꾼 뒤, 표기 줄과 같은 결과인지 `tests/test_comment_markers.py` 로 확인한다.
- 그다음 지울 것: `pieces.MARKERS` 의 `toc`·`restart`·`hide_page`·`blank_page`·`blank_lines`,
  `pieces._LIKE_MARKER`·`source.marker_typos` 의 해당 부분, `source.old_markers`, 이 표기들의 `\[` 이스케이프 설명,
  표기 줄을 쓰는 테스트(`tests/test_markers.py`, `tests/test_toc.py` 등)는 주석 마커로 옮긴다.
- 지운 뒤에는 그 줄이 글자로 들어간다 (따로 경고하지 않는다).

### 2. 남은 기존 표기를 둘지 정하기

- pandoc 표기 `\newpage`·`\pagebreak`, `{width=…}`, `::: {custom-style=…}` 는 pandoc 과 원고를 함께 쓸 수 있어 두기로 했다.
- `<!-- [cols: ...] -->` 는 이미 뷰어에 보이지 않아 비용이 작지만 `@hwpx 열너비` 와 겹친다. 둘지 정한다.
- 샘플은 pandoc 표기를 그대로 쓴다 (`samples/sample.md`, `custom-style.md`, `hide-page.md` 등). 마커로 옮길지 정한다.

### 3. 웹 페이지 변경을 실제 환경에서 확인하기

`feature/web-ui-spacing-a11y` 에서 웹 페이지(`static/index.html`)와 `web.py` 를 고쳤다 (2026-11-17, main 에 합침). 테스트와
헤드리스 Chromium 으로만 확인했고, 아래는 실제 환경에서 보지 못했다. `web` 이미지를 다시 빌드해 띄운 뒤 확인한다.

- [ ] `.env` 의 `MD2HWPX_MAX_UPLOAD_MB` 가 페이지 안내(파일·zip 탭 도움말, 선택한 파일 용량 표시)와 실제 제한에 반영되는가.
- [ ] 실제 GitLab·Gitea 로 로그인하고 돌아오면 git 저장소 탭이 선택되고, 저장소 주소·브랜치·경로·패턴이 남아 있는가.
      브랜치·경로·패턴 중 하나라도 적었으면 "선택 옵션" 이 펼쳐져 있는가. (가짜 설정으로만 시험했다.)
- [ ] 비공개 저장소에 없는 브랜치를 주면 오류가 "브랜치, 태그 또는 커밋" 입력 아래에 나오는가. (공개 저장소로만 시험했다.)
- [ ] 실제 브라우저에서:
  - [ ] Tab 으로 입력 방식 탭에 들어가 좌우 화살표로 바꿀 수 있고, 포커스 외곽선이 보이는가.
  - [ ] 변환하는 동안 경과 시간(초)이 올라가는가.
  - [ ] 파일·zip·저장소 주소를 비우고 누르면 브라우저가 그 입력을 가리키며 막는가.
  - [ ] 서버 오류가 해당 입력 아래에 빨간 글씨로 나오고 커서가 그 입력으로 가는가.
  - [ ] 다크 모드에서 체크박스·파일 선택 버튼이 어둡게 나오고 변환 버튼의 글자가 잘 읽히는가.
- [ ] 휴대폰 폭에서 화면이 잘리거나 가로로 밀리지 않는가.
- [ ] "스크립트" 탭: 다크 모드와 휴대폰 폭에서 사용법이 잘 보이는가. 내려받은 `md2hwpx-remote.py` 가 다른 PC 에서
      이 서비스로 변환하는가 (Python 3.13 으로만 돌려 보았다: 3.9, Windows 의 `python`·`py` 에서도 되는가).
- [ ] `src/` 의 코드를 바꿔 이미지를 다시 빌드하면 제목 옆의 빌드 날짜가 그날로 바뀌는가 (바꾸지 않고 다시 빌드하면 그대로인가).

PR #78 (2026-11-21) 에서 바꾼 것. 테스트로만 확인했다.

- [ ] 변환하면 브라우저가 HWPX 를 제 이름으로 내려받고, 그 파일이 한/글에서 열리는가. 응답이 JSON 으로 바뀌어 페이지가
      `hwpx` (base64) 를 풀어 저장한다. 다시 빌드해 띄운 뒤 가장 먼저 본다. 수십 MB 문서에서도 되는가.
- [ ] 경고가 많은 문서(없는 이미지 수백 개)에서도 변환되고 경고가 모두 보이는가. 프록시 뒤에서도.
- [ ] 이미 내려받아 쓰던 `md2hwpx-remote.py` 는 새 응답을 읽지 못한다: 쓰는 곳마다 다시 내려받았는가.
- [ ] `/tmp` 가 1GB 로 뜨는가 (`docker compose exec web df -h /tmp`). 쓰는 저장소 가운데 가장 큰 것이 그 안에 받아지는가.
      (`docker compose config` 로 문법만 확인했다. 모자라면 `compose.yaml` 의 `size` 를 올린다.)
- [ ] CP949 로 저장한 `.md` 를 올리면 `UTF-8 로 저장한 파일이 아닙니다` 가 페이지에 나오는가.

### 4. 스타일을 줄인 내장 템플릿을 한/글에서 열어 보기

내장 템플릿(`src/md2hwpx/template.hwpx`)에서 어디에서도 쓰지 않는 스타일 29개를 지우고 번호를 다시 매겼다 (2026-11-18, 47개 → 18개).
남긴 것: 바탕글, 본문, 개요 1~6, 표그림 제목, 표 헤더, 쪽 번호, 머리말, 각주, 미주, 메모, 요약문-본문, 표준, 표내부.
그 뒤 글머리표 목록용 `글머리표 1`~`글머리표 3` (□, ○, -) 을 더해 21개다. 글머리표 정의 둘(□, -)과 문단 모양 셋도 더했다.
지운 스타일이 쓰던 글자 모양·문단 모양은 지우지 않았다. 변환 결과는 지우기 전과 같고 스키마 검사도 통과하지만, 한/글에서는 열어 보지 못했다.

- [ ] 템플릿과 변환한 HWPX 가 한/글에서 오류 없이 열리고, 스타일 목록(F6)에 21개가 제 모양으로 보이는가.
- [ ] 글머리표 목록이 한/글에서 □ / ○ / - 로 보이고, 여러 줄 항목의 둘째 줄과 항목 안 문단·하위 목록의 자리가 어색하지 않은가.
      (왼쪽 여백 10pt / 25pt / 40pt 는 화면을 보지 않고 정한 값이다. 어색하면 템플릿의 스타일에서 고친다.)
- [ ] 글머리표와 번호를 섞은 목록의 자리가 어색하지 않은가 (PR #78 에서 바꿨다, 저장된 여백 값만 확인했다).
      글머리표 안의 번호 목록은 그 항목의 나머지 블록 자리(1수준 글머리표 안이면 25pt)에, 번호 안의 글머리표는 번호 글자 자리에
      놓인다. 스타일 개수(3)보다 깊은 목록은 더 들어가지 않고 3수준 항목의 자리에 놓인다.
- [ ] 번호 목록도 템플릿 스타일로 정하게 할지 (지금은 글머리표만).
- [ ] 지운 스타일을 `custom-style` 로 쓰던 원고가 있는가 (있으면 `템플릿에 '…' 문단 스타일이 없어` 경고가 나온다).

### 5. 미뤄 둔 것

PR #78 의 리뷰에서 찾았지만 고치지 않은 것.

- 변환 속도 (2026-11-21 에 68.0초 → 34.6초로 줄였다, [markdown-conversion.md](markdown-conversion.md) "성능"). 남은 것:
  - 실제 원고(200쪽 넘는 문서)로는 재지 않았다. 만든 문서로 쟀으므로, 실제 원고가 여전히 느리면 그것으로 다시 잰다.
    다이어그램이 많은 원고는 `mmdc` 가 다이어그램마다 Chromium 을 띄우는 시간이 따로 든다 (재지 않았다).
  - 넣을 수 없는 이미지를 찾느라 변환이 이미 읽은 이미지를 다시 푼다 (SVG 는 `rsvg-convert` 를 한 번 더). 그림 40개에 1~2초.
  - 남은 시간은 python-hwpx 안이다: 저장(직렬화·검증)이 3분의 1, 각주 번호 계산(각주마다 문서 전체를 센다), 코드블록의 줄 높이 재기.
- 업로드 크기 제한(`MD2HWPX_MAX_UPLOAD_MB`)은 요청 본문을 다 받은 뒤에 적용된다. 내부망 전용이라 `/tmp` 의 1GB 로 막는다.
  밖에 열게 되면 `Content-Length` 를 먼저 보거나 앞단 프록시에서 제한한다. git 저장소 크기도 `/tmp` 의 크기만이 제한이다.
- front matter: 수평선으로 시작하는 문서의 다음 줄이 `머리말: 내용` 처럼 `키:` 꼴이면 여전히 front matter 로 읽는다.
- 세션은 프로세스 메모리에 있다: uvicorn 워커를 둘 이상 쓰려면 세션을 쿠키나 공유 저장소로 옮겨야 한다.
